Chrome Extension

The MV3 sideloaded extension is the only thing in SuperSurf that actually touches the browser. It runs DOM work through content scripts in an isolated world (invisible to page JavaScript) and reserves chrome.debugger for screenshots, network interception, and JS evaluation. Everything else — daemon, server, scheduler — exists to feed JSON-RPC commands to this one process.

1. Overview & MV3 model

SuperSurf is a Manifest V3 extension. The MV3 service worker model is the dominant constraint on every other design decision in this package:

  • Service workers are not persistent. Chrome terminates them after ~30s of inactivity and reanimates them on events.
  • setTimeout and setInterval die when the worker dies. Anything that needs to survive suspension must use chrome.alarms.
  • All chrome.* event listeners must be registered at the top level of background.ts, not inside async callbacks. Otherwise the worker won't wake on the event the listener was supposed to handle.
  • State that needs to survive suspension is mirrored to chrome.storage.session, which is in-memory but process-survival.
MV3 trap Async IIFE initialization (the bottom half of background.ts) runs only on first wake. Any listener registered inside the IIFE will fail to fire if the worker was woken by that very event. The fix is what background.ts:46-119 does — lifecycle, tabs.onCreated, tabs.onUpdated, and webNavigation.onBeforeNavigate are all registered at the module top level. The IIFE handles initialization-only work.

Content-script-first vs CDP

Two privileged channels into the page exist: content scripts (isolated world, invisible to page JS) and chrome.debugger (CDP through the extension wrapper). SuperSurf's rule is fixed: DOM reads/writes go through content scripts; CDP is reserved for the things that genuinely require it — screenshots (Page.captureScreenshot), network interception (Network.* events), evaluation (Runtime.evaluate), CSS inspection (CSS.*), and mouse humanization (Input.dispatchMouseEvent). Rationale lives in architecture §7 and in knowledge/chat/supersurf-browser-automation.md.

3. Service worker (background.ts)

The single largest file in the extension at ~680 lines. Acts as coordinator for every other subsystem: WebSocket lifecycle, command handler registry, CDP debugger lifecycle, tab buffer, alarm dispatch, popup IPC.

Module structure

The file is split into two halves:

  1. Top-level (lines 36-119) — chrome event listeners that must be registered synchronously at module load. These survive worker termination and wake the worker on events.
  2. Async IIFE (lines 122-683) — one-shot initialization: create handler instances, wire injectors, fetch the domain whitelist, register all the JSON-RPC command handlers, then await wsConnection.connect().

Top-level listeners

EventPurpose
runtime.onInstalled (background.ts:46) On first install, opens dist/pages/welcome.html.
runtime.onStartup (background.ts:51) No-op body; existence forces SW activation on browser launch.
tabs.onCreated (background.ts:60) Fills spawnedTabBuffer — 10s rolling window of new tabs that the drainSpawnedTabs handler returns to detect popup-spawned tabs from clicks.
tabs.onUpdated (background.ts:70) Pushes tab_info_update notifications to the daemon when the attached tab's URL changes.
webNavigation.onBeforeNavigate (background.ts:91) Domain whitelist enforcement — reverts the tab to its previous URL if the destination isn't allowed, then notifies the server.

CDP debugger lifecycle

Defined at background.ts:261-297. Two helpers:

  • ensureDebugger(tabId) — idempotent attach. Detaches first if currently attached to a different tab (Chrome only allows one debugger per tab, but we hold one debugger across many tabs by reattaching). Enables five domains: Network, DOM, CSS, Runtime, Page.
  • cdp(tabId, method, params, timeout=50000) — auto-attaches, then races chromeDebugger.sendCommand against a 50s timeout. Hangs are real — CDP commands occasionally never complete and the timeout is the only way out.

Note the bracket-notation hack on line 36:

const chromeDebugger = (chrome as any)['debugger'] as ChromeDebugger;

debugger is a JS reserved word, so chrome.debugger can't be referenced via dot syntax in TypeScript without any-casting. Same hack appears in chrome.d.ts.

Profile registration

Two related chrome.runtime.onMessage listeners (background.ts:229-241) and a chrome.storage.onChanged listener (background.ts:245-253) implement the profile flow:

  1. Daemon spawns Chromium with first-launch URL http://127.0.0.1:5555/register/<name>.
  2. That HTML page calls window.postMessage({ __supersurf: true, action: 'register-profile', profile }).
  3. Content script (content-script.ts:37-52) catches the postMessage and forwards as chrome.runtime.sendMessage({ type: 'profileRegister', profile }) with up to 10 retries (the SW may not be ready on first install).
  4. Background writes the name to chrome.storage.local and closes the registration tab.
  5. The storage.onChanged listener then triggers a WebSocket disconnect/reconnect so the daemon's matchmaker can bind this connection to the profile.

4. WebSocket connection (connection/websocket.ts)

WebSocketConnection is the JSON-RPC 2.0 client for the daemon. Single connection, auto-reconnect via Chrome alarms, command + notification handler maps populated by background.ts.

Lifecycle

connect()                                       (websocket.ts:112)
  -> isExtensionEnabled()  storage.local.extensionEnabled !== false
  -> getConnectionUrl()    ws://127.0.0.1:<mcpPort|5555>/extension
  -> new WebSocket(url)
  -> _handleOpen()         (websocket.ts:188)
       send handshake { type, browser, version, buildTimestamp, profile? }
disconnect()                                    (websocket.ts:154)
  -> alarms.clear('ws-reconnect')
  -> socket.close()
  -> iconManager.setConnected(false)

Profile resolution

_resolveProfile() (websocket.ts:216) is handshake-time profile lookup with a fallback chain:

  1. Primary: chrome.storage.local.supersurf_profile.
  2. Fallback: chrome.cookies.get on http://127.0.0.1:<mcpPort> for the supersurf_profile cookie that the daemon's registration page set with SameSite=Lax. On hit, backfills storage.local for next time.

This dual path is why the daemon's registration URL also sets a cookie — if extension storage gets wiped (force-killed Chromium, manual extension removal), the cookie is the one source of truth that survives.

Reconnect via Chrome alarms

Why chrome.alarms and not setTimeout:

Don't use setTimeout in MV3 Chrome can suspend the service worker before any pending setTimeout fires. The reconnect callback would silently vanish and the extension would never reconnect after a brief network blip. chrome.alarms are owned by the browser and wake the SW from cold sleep. SuperSurf uses alarms.create('ws-reconnect', { when: Date.now() + 5000 }) with a reconnectTimeout guard flag to prevent stacking.

Message routing

_handleMessage() (websocket.ts:248) splits inbound messages into three classes:

  • error field set: log and drop.
  • Notification (method set, no id): dispatch to notificationHandlers. Special-cased authenticated notifications populate projectName.
  • Command (has id + method): look up commandHandlers, await, attach a _recovery note if ensureAttachedTab() had to swap tabs mid-call, send back JSON-RPC response.

Tab recovery note

The recovery-note plumbing (setRecoveryNoteProvider at websocket.ts:62, consumed at websocket.ts:275-286) lets TabHandlers.ensureAttachedTab() (the auto-recovery path when the attached tab is null or stale) attach a structured {reason, previousTabId, newTabId, url} field to the command response. This shows up in the agent's tool result so the LLM sees that the attached tab silently changed.

5. Session context (session-context.ts)

Centralizes per-session state in one object. Replaces the prior scattered approach where TabHandlers, IconManager, and background.ts all owned their own copies of “attached tab” and “stealth mode.”

Multi-session vs single-client

The daemon's scheduler injects a _sessionId into every tab-scoped command, so the extension can isolate state per MCP session. SessionContext supports both modes:

  • Multi-session: ctx.getSession('client-abc-123') returns the named session's state.
  • Single-client (backwards compat): ctx.attachedTabId, ctx.stealthMode, ctx.cursorPositions, etc. delegate to the null-keyed session (session-context.ts:170-203).

State shape

interface SessionState {
  attachedTabId: number | null;
  stealthMode: boolean;
  stealthTabs: Map<number, boolean>;          // per-tab override
  cursorPositions: Map<number, {x, y}>;         // for mouse humanization continuity
  humanizationConfig: { enabled: boolean };
}

Persistence

Every setter calls persist(), which write-throughs to chrome.storage.session under __supersurf_session_state. Maps serialize to entry-arrays. On worker wake, init() calls rehydrate() to restore. clearStorage() is called on disable/disconnect so the keyspace doesn't grow unbounded across enable/disable cycles in a long browser session.

6. Command handlers

Five handler classes under extension/src/handlers/. Each is instantiated once in the IIFE and registered onto WebSocketConnection by name.

TabHandlers (handlers/tabs.ts)

Tab CRUD with two non-obvious responsibilities:

  • Tab group isolation (tabs.ts:225-305): Each MCP session gets a chrome.tabGroups group with a rotating color from GROUP_COLORS. selectTab refuses to attach to tabs in another session's group; ungrouped tabs are claimed on first selection. handleSessionDisconnect ungroups everything when the MCP session ends.
  • ensureAttachedTab() (tabs.ts:117-196) — called at the top of every tab-scoped handler. If attachedTabId is null or stale (the tab was closed), it picks a recovery candidate (active tab in current window > any active tab > last automatable tab), updates state, and returns a recovery object that the WebSocket layer attaches to the response as _recovery.

NetworkTracker (handlers/network.ts)

500-entry FIFO ring buffer keyed by requestId. Tracks four chrome.webRequest events: onBeforeRequest, onBeforeSendHeaders, onCompleted, onErrorOccurred. Headers are flattened from Chrome's [{name, value}] form to a plain object. The CDP-side tracker in background.ts:182-218 runs in parallel for cases where webRequest doesn't see the request (e.g. the initial document load).

ConsoleHandler (handlers/console.ts)

1000-message FIFO buffer. Capture is via MAIN-world injection (scripting.executeScript({ world: 'MAIN' })) that monkey-patches console.log/warn/error/info/debug. The patched methods postMessage back to the page, content-script.ts relays to the SW, ConsoleHandler buffers. Idempotent per tab via the __supersurfConsoleInjected marker.

DialogHandler (handlers/dialogs.ts)

MAIN-world inject that overrides window.alert, window.confirm, window.prompt with non-blocking stubs. Each stub pushes a {type, message, response, timestamp} entry to window.__supersurfDialogEvents and returns the configured value (accept: true/false, promptText). Without this, page dialogs would block automation indefinitely.

DownloadHandler (handlers/downloads.ts)

Wraps chrome.downloads.download with a chrome.downloads.onChanged listener that watches for state.current === 'complete' or 'interrupted'. 5-minute timeout. On success returns {filePath, fileSize, mimeType} from downloads.search({id}).

7. Content script (content-script.ts)

Injected at document_start, top frame only, <all_urls>. Two responsibilities, both window.message-driven:

Console relay

Listens for { __supersurfConsole: { level, text, timestamp } } postMessages from the MAIN-world console patch and forwards via chrome.runtime.sendMessage({type: 'console', ...}). The isolated-world content script is the bridge between MAIN-world page context and the service worker.

Profile registration relay

Listens for { __supersurf: true, action: 'register-profile', profile } from the daemon's /register/<name> HTML page, forwards as {type: 'profileRegister', profile} with up to 10 retries spaced 500ms apart (the SW may not be ready on first install). See §3 for the receiving end.

Tech stack detection

detectTechStack() (content-script.ts:70) runs 1s after DOMContentLoaded and probes for ~40 frameworks/libraries. Output is sent as {type: 'techStack', data} and surfaces in browser_tabs output for each tab.

8. Secure-fill (secure-fill.ts + background.ts:560)

Credential injection that never crosses the agent boundary:

  1. Agent calls secure_fill with an env var name (e.g. $LOGIN_PASSWORD). The agent never sees the value.
  2. Server resolves the env var locally (server/src/dotenv.ts + process env) and forwards {selector, value} over the daemon socket.
  3. Extension injects a MAIN-world function via chrome.scripting.executeScript({world: 'MAIN'}) with args: [selector, value].
  4. The injected function types char-by-char with 40 + Math.random() * 80ms per keystroke (~40-120ms range), dispatching the full focus → keydown → input → keyup → change event sequence per character.

The standalone secure-fill.ts module is the extracted/exported version; background.ts inlines an equivalent function body inside executeScript({func}) because executeScript serializes the function and captures no closures. Edits must stay in sync.

Why MAIN world Isolated-world content scripts can't fire native input events that page-level frameworks (React controlled inputs, Angular reactive forms) listen on. MAIN world runs in the page's own context, so framework input listeners actually fire and validation passes.

9. Domain whitelist (domain-whitelist.ts)

Optional safety rail that restricts automated navigation to the Tranco top 100K domains. Off by default; toggled in the popup Settings view.

Design rules

  • Passthrough on disabled / empty / special schemes (domain-whitelist.ts:102-110). The whitelist must never lock the user out of about:blank or chrome://.
  • Suffix-walk matching (domain-whitelist.ts:122-127). For mail.google.com, walks mail.google.com → google.com → stops before bare TLD. Whitelisting google.com allows all subdomains.
  • Cache for 24h in chrome.storage.local — keyed by domainWhitelistData + domainWhitelistLastFetch. Refresh runs on the whitelist-refresh alarm.

Tranco fetch + ZIP parsing

The Tranco list ships as a ZIP-compressed CSV (https://tranco-list.eu/top-1m.csv.zip). The extension has zero runtime deps, so parsing is hand-rolled in _extractZip() (domain-whitelist.ts:194-237):

  1. Read local file header with DataView at offsets 0/8/18/26/28 (signature, compression method, compressed size, filename length, extra length).
  2. If method 0 (stored), TextDecoder the bytes directly.
  3. If method 8 (deflate), pipe through new DecompressionStream('deflate-raw').
  4. CSV parse: take first 100K lines, return line.split(',', 2)[1].

Browser-native DecompressionStream is the trick that avoids pulling in pako or another ZIP library.

Enforcement

The top-level webNavigation.onBeforeNavigate listener in background.ts:91 fires on the attached tab's top-frame navigation. If the URL fails isDomainAllowed, the listener calls chrome.tabs.update(tabId, {url: previousUrl || 'about:blank'}) to revert, then notifies the server with notifications/navigation_blocked.

10. Popup UI (popup/)

Three files: popup.html (skeleton), popup.css, and the TS pair popup.ts + popup.templates.ts. Pattern is deliberately framework-free — one mutable state singleton, one render() that swaps innerHTML, one attachEventListeners() that re-binds.

Two views

  • Main (renderMain): connection status dot (connecting / connected / disconnected), tab automated flag, project name from the server's authenticated notification, profile badge if a managed profile is active, stealth indicator, enable/disable toggle.
  • Settings (renderSettings): MCP port (default 5555), Debug Mode checkbox, Domain Whitelist checkbox.

Background IPC

chrome.runtime.sendMessage with one of: getStatus, enableExtension, disableExtension, enableWhitelist, disableWhitelist, getWhitelistStats. The popup also listens to statusChanged messages (broadcast by the SW on connect/disconnect) and storage.onChanged for live updates without polling.

12. Experimental subsystems (experimental/)

experimental/index.ts

Registers capturePageState and waitForReady command handlers. waitForReady races waitForDOMStable (via scripting.executeScript) against pollNetworkIdle (every 100ms, looking for a quiet window of idleMs) against an overall timeout.

experimental/capture-page-state.ts

Self-contained injectable function that walks document.querySelectorAll('*') and returns a PageState: visible element count, deduped 200-char text snippets, shadow-root count, iframe count, hidden-element count, form values (passwords masked, checkboxes summarized as checked/unchecked). Used by the server's page-diffing experiment to compare snapshots before/after an action.

No closures, no imports chrome.scripting.executeScript({func}) serializes the function body via toString() and runs it in a fresh page context. Imports, closure-captured variables, and TypeScript enums silently break. Both capturePageState and waitForDOMStable are intentionally written without external references.

experimental/wait-for-ready.ts

Mutation-observer-based DOM stability detector. Each mutation resets a debounce timer; resolves when stabilityMs elapse with no childList/subtree mutations. Always resolves — never rejects.

experimental/mouse-humanization.ts

Three handlers:

  • humanizedMouseMove: replays server-generated Bezier waypoints via cdp(tabId, 'Input.dispatchMouseEvent', {type: 'mouseMoved', x, y}), await sleep(wp.delayMs) between points. Stores last position in sessionContext.cursorPositions for path continuity.
  • setHumanizationConfig: turns the experiment on/off; on enable, schedules the mouse-idle-drift alarm with 10-30s random delay.
  • getViewportDimensions: Runtime.evaluates {width: window.innerWidth, height: window.innerHeight} so the server can clamp generated paths.

handleIdleDrift() is fired from the alarm dispatcher in background.ts:175: if humanization is still enabled, dispatch a 2-5px random drift and reschedule.

13. Security — secure_eval Layer 2

The extension hosts Layer 2 of the three-layer secure_eval pipeline. Layer 1 (server-side AST analysis via acorn) catches statically detectable patterns. Layer 2 (this) catches dynamic/runtime access by running agent code against a deep Proxy membrane with no real DOM. Layer 3 is page-context Runtime.evaluate.

security/secure-eval/index.ts registers the validateEval command. The handler builds a fresh Function wrapped in with(membrane) { (function() { "use strict"; ...code... })(); } and runs it; any Error whose message starts with [secure_eval:membrane] means the code reached a blocked terminal (fetch, eval, localStorage, WebSocket, XMLHttpRequest, etc.) and the response is {safe: false, reason}.

Graduated from experiment in v1.11.0. Full details — threat model, blocked terminal list, why with-membrane works, known bypasses — live in Trust Boundaries & Security.

TL;DR
One MV3 service worker (background.ts), one WebSocket to the daemon, ~20 JSON-RPC command handlers, a strict content-script-first vs CDP split. Every async timer is a chrome.alarms entry because MV3 kills setTimeout. State persists through SW suspension via SessionContext write-through to chrome.storage.session. Profile binding flows from a daemon HTML page → postMessage → content script → SW → storage.local → reconnect handshake, with a cookie fallback through chrome.cookies. Zero runtime dependencies — even ZIP decompression of the Tranco list uses native DecompressionStream.
