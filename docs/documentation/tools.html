Browser Tools Reference

Every browser tool the agent can call goes through one orchestrator (BrowserBridge) and one switch (dispatchTool) before reaching a per-tool handler. Almost every handler is content-script-first — DOM reads and writes happen in the extension's isolated world via Runtime.evaluate, with selector-based actions auto-falling-back to a DFS walk of child iframes when the top frame doesn't resolve. Raw CDP is reserved for screenshots, network capture, and PDF generation.

1. Dispatch model

The MCP server lazily constructs a BrowserBridge (server/src/tools.ts:36) on connect. The bridge owns no per-tool logic: it builds a ToolContext object and forwards every call to dispatchTool in server/src/tools/lib/dispatcher.ts:48, which is one big switch statement keyed by the MCP wire name.

MCP CallTool ─▶ BrowserBridge.callTool(name, args) │ │ if !ext: short-circuit with "Extension not connected" │ build ToolContext { ext, cdp, eval, getElementCenter, ... } ▼ dispatchTool(ctx, name, args, options, env) │ switch (name) ────┼──▶ onBrowserTabs (navigation.ts) ├──▶ onNavigate (navigation.ts) ├──▶ onInteract (interaction/index.ts) ├──▶ onSnapshot/Lookup/... (content.ts) ├──▶ onGetElementStyles (styles.ts) ├──▶ onScreenshot/PdfSave (screenshot.ts) ├──▶ onEvaluate (browser_evaluate/index.ts) ├──▶ onConsoleMessages (network.ts) ├──▶ onFillForm/Drag/Secure (forms.ts) ├──▶ onWindow/Dialog/Verify (misc.ts) ├──▶ onNetworkRequests (network.ts) ├──▶ onListExtensions (misc.ts) ├──▶ onPerformanceMetrics (misc.ts) ├──▶ onBrowserDownload (downloads.ts) └──▶ default ──▶ callExperimentalTool() (browser_storage) │ ▼ maybeAppendScreenshot ─▶ inline screenshot if args.screenshot=true │ ▼ finally: writeAuditEntry + maybe append tip text

Three concerns are pulled out of every handler:

  • Audit log — the dispatcher's finally block writes a redacted NDJSON entry per call (dispatcher.ts:125-145). Always-on. See §2.6.
  • Tip rendering — the same finally block may append a contextual hint when the agent reaches for the wrong tool (e.g. browser_evaluate for a click). See §2.5.
  • Screenshot inline — tools in SCREENSHOT_ELIGIBLE can attach a fresh capture when the agent passes screenshot: true (result-formatter.ts:17-20, 95-129).

The dispatcher also rewrites a specific class of errors on the way out: CDP attach/detach conflicts with other extensions (iCloud Passwords, password managers) get a "Possible extension conflict" hint with a fix-it path (dispatcher.ts:113-122).

2. Cross-cutting primitives

2.1 ToolContext

Every handler receives the same ToolContext object, defined in server/src/tools/lib/types.ts:31-53. It exposes the subset of BrowserBridge internals handlers need without leaking the transport or connection manager directly:

interface ToolContext {
  ext: IExtensionTransport;            // for ext.sendCmd('snapshot', ...) etc.
  connectionManager: any;              // attached tab, stealth, statusHeader

  cdp(method, params?): Promise<any>;   // forward a CDP command via the extension
  eval(expression, awaitPromise?): Promise<any>;   // page-context Runtime.evaluate
  sleep(ms): Promise<void>;
  getElementCenter(selector): Promise<{x,y}>;      // top-frame only; throws "Did you mean?"
  getSelectorExpression(selector): string;          // CSS selector → JS expression
  findAlternativeSelectors(selector): Promise<any[]>;

  formatResult(name, result, options): any;
  error(message, options): any;
}

The factory is BrowserBridge.buildContext() (server/src/tools.ts:71-88) — CDP/eval are bound to the current extension transport, and the formatter is bound to the connection manager so handlers don't have to know about either.

2.2 Frame-aware primitives

This is the single design choice that distinguishes browser_interact and browser_fill_form from naive CDP automation: every selector-based action transparently walks child iframes when the top frame misses. The helpers live in server/src/tools/lib/frames.ts.

FunctionFile:LineRole
findElementInFrames frames.ts:12 DFS-walk the frame tree via Page.getFrameTree; for each child frame, create an isolated world (Page.createIsolatedWorld) and try the selector. Returns the first hit's { objectId, contextId, frameId }.
resolveInFrames frames.ts:68 Top-frame-first wrapper. Tries Runtime.evaluate in the default context, falls back to findElementInFrames on miss. Returns contextId: null when the element was found at top.
evalInFrameOrTop frames.ts:88 Evaluate an expression in either a child-frame isolated context (if contextId is set) or top-frame default context. Mirrors ctx.eval's exception semantics.
getCenterInFrame frames.ts:123 Top-frame viewport coordinates for any element — even nested inside multiple iframes. Walks ancestor iframes accumulating offsets via DOM.getFrameOwner + callFunctionOn(getBoundingClientRect).
Why coordinate accumulation? DOM.getBoxModel and getBoundingClientRect() return iframe-local coordinates for nodes inside iframes. Click dispatch (Input.dispatchMouseEvent) requires top-frame viewport coords, so getCenterInFrame walks up the frame tree summing each ancestor iframe's top-left offset (frames.ts:123-209). Same approach Playwright and Puppeteer use.

2.3 Element resolver

server/src/tools/lib/element-resolver.ts handles selector parsing and best-effort failure hints:

  • getSelectorExpression (element-resolver.ts:30) — converts a CSS selector (with optional SuperSurf-only :has-text("...") suffix) to a JS expression that returns the matching Element or null. The :has-text() form expands to a querySelectorAll+textContent.includes loop.
  • Digit-leading ID rewrite (rewriteDigitLeadingIds, element-resolver.ts:17) — rewrites #883a76-foo to [id="883a76-foo"] because CSS spec disallows ID identifiers that start with a digit, but Ashby and other apps emit them anyway.
  • getElementCenter (element-resolver.ts:114) — resolves a selector to its top-frame viewport-center coordinates. On miss, throws an Error with "Did you mean?" suggestions when the selector contains :has-text(...).
  • findAlternativeSelectors (element-resolver.ts:53) — on miss, scans the DOM for up to 3 visible + 2 hidden elements whose direct text content matches the :has-text argument and returns guessed selectors.

2.4 Result formatter & status header

Every non-raw response goes through formatResult (server/src/tools/lib/result-formatter.ts:37), which:

  1. Prepends a status header line built by connectionManager.statusHeader() (URL, attached tab id, stealth flag, browser name).
  2. Unwraps the _recovery envelope — when the extension's ensureAttachedTab() rebinds a stale tab mid-call, the header gets a ↻ tab recovered: ... line (result-formatter.ts:46-61).
  3. Syncs attachedTab, browserName, and stealthMode from the result back to the ConnectionManager so future status headers stay accurate.
  4. For browser_take_screenshot with data, returns two content blocks: a text block (header + message) and an image block (base64).

Errors flow through formatError (result-formatter.ts:132) which produces an MCP error block (### Error\n\n...) or, in rawResult mode, a plain { success: false, error } object.

2.5 Tip registry

server/src/tips.ts is a priority-ranked rule set (TIPS, tips.ts:51-210) that fires when an agent uses a tool in a way another tool would handle better. The dispatcher calls getTip(name, args, result, error, sessionId) in its finally block (dispatcher.ts:128) and, if a rule matches, appends the message to both the response text and the audit entry.

Examples (highest priority first):

  • interact-no-tab-attached (priority 5) — on browser_interact error matching /no tab attached/i: point at browser_tabs action='attach'.
  • eval-click-to-interact (priority 10) — browser_evaluate with .click(): redirect to browser_interact with :has-text("...").
  • eval-dispatchevent-to-interact (priority 15) — explicitly calls out that synthetic dispatchEvent is detectable, real CDP input events are not.
  • eval-value-to-fill-form, eval-scroll-to-interact, eval-location-to-navigate, eval-queryselector-to-lookup, eval-innerhtml-to-extract, eval-computedstyle-to-styles — the full set of "use the dedicated tool" hints.
Suppression Tips suppress after firing 3 times in a row for the same (session, tool, tip_id) tuple (SUPPRESS_AFTER = 3, tips.ts:20). One miss resets the counter for that tip only — tip A firing doesn't reset tip B (tips.ts:236-247).

2.6 Audit logging

Every tool call writes one line to ~/.supersurf/logs/sessions/audit-{sessionId}-{timestamp}.ndjson. The logger is in server/src/audit-logger.ts (always-on, not gated behind DEBUG_MODE).

Each entry contains: ts, version, session_id, tool, redacted params, result (ok|error), error message, current url, duration_ms, experiments snapshot, and tip if one fired (audit-logger.ts:40-53).

Two redaction passes:

  • Sensitive keys redacted — any param whose lowercase name is in { value, password, token, secret, credential } is replaced with [REDACTED] (audit-logger.ts:25).
  • Stripped keys — data (screenshot blobs, base64 PDFs) is dropped entirely (audit-logger.ts:28).

For details on log location, retention, and the trust posture, see Server Core.

2.7 Path sandbox

server/src/tools/lib/sandbox.ts exports sandboxPath, used by browser_take_screenshot (file save), browser_pdf_save, and browser_download to resolve agent-supplied paths. All paths are resolved relative to $HOME. Absolute paths like /etc/foo get rewritten to $HOME/etc/foo; traversal that escapes $HOME throws Permission denied (sandbox.ts:25-38).

3. Navigation

browser_tabs

List, create, attach, or close browser tabs. Must be the first tool the agent calls on a fresh connection — no other tool works without an attached tab.

action: 'list' | 'new' | 'attach' | 'close'
url?: string                  // for new
index?: number                // for attach/close (display order)
tabId?: number                // for attach (more stable than index)
activate?: boolean            // default true for new, false for attach
stealth?: boolean             // toggle bot-detection avoidance

Handler: onBrowserTabs — server/src/tools/navigation.ts:22.

Schema: tools/schemas.ts:22-46.

Forwards to extension commands getTabs, createTab, selectTab, closeTab. On new / attach, sets connectionManager.attachedTab so the status header on every subsequent response reflects the active tab.

Index vs tabId Index is display order and shifts when other tabs open or close. tabId is the Chrome-assigned numeric ID, stable across reorderings. Prefer tabId when you have it.

browser_navigate

Go to a URL, navigate back/forward, or reload.

action: 'url' | 'back' | 'forward' | 'reload' | 'test_page'
url?: string         // required when action='url'
screenshot?: boolean // capture and inline a screenshot after the action

Handler: onNavigate — server/src/tools/navigation.ts:72.

Schema: tools/schemas.ts:49-66.

The back and forward branches use page-side window.history.back()/forward() rather than CDP navigation events, then read window.location.href to report the resulting URL.

Wait behavior After a URL load, onNavigate waits 1500ms by default (navigation.ts:95). When the smart_waiting experiment is enabled, it instead calls ext.sendCmd('waitForReady', { timeout: 10000, stabilityMs: 500 }) — the extension polls until DOM mutation rate stays below threshold (navigation.ts:91-96, 102-108, 113-119, 124-128). The screenshot path uses extension-side wait so the capture lands after stability, not at the raw load event.

4. Interaction

browser_interact

Run a sequence of page interactions. The single most-used tool. Each call takes an array of action objects executed in order; onError: 'stop' (default) aborts on the first failure, 'ignore' continues.

actions: Array<{
  type: 'click' | 'type' | 'clear' | 'press_key' | 'hover' | 'wait'
      | 'mouse_move' | 'mouse_click' | 'scroll_to' | 'scroll_by'
      | 'scroll_into_view' | 'select_option' | 'select_custom'
      | 'file_upload' | 'force_pseudo_state'
  selector?: string        // CSS selector or `tag:has-text("text")`
  text?: string            // for type
  key?: string             // for press_key
  value?: string           // for select_option / select_custom
  files?: string[]         // for file_upload
  pseudoStates?: string[]  // for force_pseudo_state
  x?, y?, button?, clickCount?, timeout?: number
}>
onError?: 'stop' | 'ignore'      // default 'stop'
screenshot?: boolean             // inline screenshot after final action

Handler: onInteract — server/src/tools/interaction/index.ts:45. Per-action implementations register themselves at module load via registerAction (interaction/registry.ts:7); the barrel imports at interaction/index.ts:20-32 trigger registration.

Schema: tools/schemas.ts:69-124.

Action handlers (one file per action, all under server/src/tools/interaction/):

ActionFile:LineNotes
clickclick.ts:6 CDP Input.dispatchMouseEvent press/release with random 78–142ms hold; iframe-aware via getCenterInFrame; emergency DOM el.click() fallback for anchors and onclick handlers; detects spawned tabs.
typetype.ts:4 Focus then Input.dispatchKeyEvent char-by-char; reads back the field value in the same frame context for echo.
clearclear.ts:4 Set el.value = '' + dispatch input/change events.
press_keypress-key.ts:4 Maps named keys (Enter, Tab, ArrowDown, etc.) via KEY_MAP and dispatches a keyDown/keyUp pair.

scroll_to / scroll_by / scroll_into_view scroll.ts:4-70 Element-scoped or window-scoped scroll; iframe-aware via resolveInFrames.
select_optionselect-option.ts:4 Native <select>: native setter + input/change events. Throws not a <select> on non-native widgets, which trips the interact-not-native-select tip.

Iframe auto-fallback Every selector-based action uses resolveInFrames or getCenterInFrame, both of which try the top frame first and DFS-walk child frames on miss. Agents don't need to know about iframe boundaries — this was previously a major class of agent failure that forced browser_evaluate spirals.
Smart waiting integration The click handler triggers waitForReady after the click when the smart_waiting experiment is on (click.ts:40-43) — useful for SPAs where a click triggers a route change but no full navigation event.
Page diffing wraps the whole sequence When page_diffing is enabled, onInteract captures a DOM snapshot before the first action and after the last, then appends a markdown diff section listing added/removed text and form value changes (interaction/index.ts:50-58, 76-90). Confidence below 0.5 is reported as "full re-read recommended".

5. Content extraction

browser_snapshot

Return the page's accessibility tree as indented role/name pairs, with a form-fields appendix.

Handler: onSnapshot — server/src/tools/content.ts:78. Schema: tools/schemas.ts:127-132.

Extension fetches the AX tree via snapshot; if no formFields array is included, the server fills it in with a page-side eval that walks input/textarea/select, attaches label/aria-label/placeholder, and captures option lists for <select>. InlineTextBox nodes with the same parent are coalesced into one node (coalesceInlineTextBoxes, content.ts:29-72) because Chrome splits long text runs into one node per visual line.

browser_lookup

Find elements by visible text, return selectors + viewport coordinates. Visible matches first, hidden last, capped at limit (default 10).

text: string
limit?: number   // default 10

Handler: onLookup — server/src/tools/content.ts:178. Schema: tools/schemas.ts:135-148.

Returns { selector, tag, visible, text, x, y, width, height, formField? } per match. Form fields get an extra block with label, type, required, and option list.

browser_extract_content

Convert page content to clean markdown with pagination.

mode?: 'auto' | 'full' | 'selector'   // default 'auto'
selector?: string                       // mode='selector'
max_lines?: number                      // default 500
offset?: number                         // for pagination

Handler: onExtractContent — server/src/tools/content.ts:286. Schema: tools/schemas.ts:151-169.

auto tries article, main, [role="main"], .content, .post, #content in order, falling back to document.body on no match. full always uses body. selector targets a single element. Truncation footer reports showing X of Y lines, offset=N when more remains.

browser_get_element_styles

DevTools Styles panel for agents. Returns matched + inline + computed CSS with applied / overridden / computed markers.

selector: string
property?: string                  // filter to one CSS property
pseudoState?: string[]             // hover, active, focus, visited, focus-within,
                                   // focus-visible, target

Handler: onGetElementStyles — server/src/tools/styles.ts:36. Schema: tools/schemas.ts:172-193.

Resolves nodeId via DOM.getDocument + DOM.querySelector, optionally calls CSS.forcePseudoState, then merges CSS.getMatchedStylesForNode output with stylesheet filename + line number heuristics. Cleans up forced pseudo-states on exit (styles.ts:151-156).

6. Forms

browser_fill_form

Set values on multiple form fields in one call. Per-field iframe walk and per-field read-back verification.

fields: Array<{ selector: string; value: string }>
screenshot?: boolean

Handler: onFillForm — server/src/tools/forms.ts:32. Schema: tools/schemas.ts:278-301.

Uses native prototype setters (Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set) to bypass framework-managed value properties — the React value tracker (per facebook/react#10135) only diffs when the underlying setter is invoked. Fires input → microtask yield → change → microtask yield → blur in that order to give React time to reconcile before validation handlers run (forms.ts:84-94).

After each field is set, the handler reads the DOM value back in the same frame context and prefixes the result with ✓ (verified) or ⚠ (mutation ran but read-back didn't confirm) (forms.ts:104-124).

Verified ≠ submitted The verify step catches loud failures (wrong selector, disabled input, rejected value). It does not catch React's silent value-tracker drift, where the field reads correctly but the form's React state disagrees. Re-check before submitting forms when stakes matter.

browser_drag

Drag one element onto another via simulated CDP mouse events.

fromSelector: string
toSelector: string
screenshot?: boolean

Handler: onDrag — server/src/tools/forms.ts:137. Schema: tools/schemas.ts:304-317.

Resolves both elements via ctx.getElementCenter (top-frame only — no iframe walk), presses at source, interpolates 10 mouseMoved steps to target, releases.

secure_fill

Type credentials from server-side environment variables into a form field without ever exposing the value to the agent.

action: 'fill' | 'list'
selector?: string             // required for fill
credential_env?: string       // env var name, e.g. "MY_PASSWORD"

Handler: onSecureFill — server/src/tools/forms.ts:181. Schema: tools/schemas.ts:445-467.

list reads .env via getDotenvKeys() (server/src/dotenv.ts) and returns the variable names only — never values. fill resolves process.env[envName] server-side and pipes the raw string to ext.sendCmd('secure_fill', { selector, value }); the extension types it char-by-char with randomized 40–120ms delays. The credential value never appears in MCP responses, the audit log (value is in the redacted set), or extension logs.

11. Evaluate

browser_evaluate

Run JavaScript in the page context for read-only computation and return the result. Defended by secure_eval — the AST analyzer + Service Worker membrane + page-context Proxy stack — which blocks network calls, storage access, navigation, click simulation, and dynamic-code primitives by default.

function?: string      // wrapped as IIFE: (fn)()
expression?: string
purpose: string        // REQUIRED — explains why dedicated tools don't fit;
                       // logged in audit trail

Handler: onEvaluate — server/src/tools/browser_evaluate/index.ts:28. Schema: tools/schemas.ts:226-258.

The handler runs three checks before passing code to the page:

  1. Layer 1 — AST static analysis (~1ms). analyzeCode in browser_evaluate/secure-eval.ts uses acorn + acorn-walk to scan for fetch, XMLHttpRequest, WebSocket, localStorage/sessionStorage, document.cookie, window.location writes, eval, Function constructor, click/dispatchEvent on elements, and dynamic property access patterns. Blocked code returns a structured analysis.reason the user sees inline.
  2. Layer 2 — Service Worker Proxy membrane (~10–20ms). ext.sendCmd('validateEval', { code }) — the extension's security/secure-eval/membrane.ts wraps the code execution in a deep Proxy that traps blocked terminal API access. If the extension doesn't support validateEval (older builds), Layer 1+3 still cover.
  3. Layer 3 — Page-context Proxy wrapper. wrapWithPageProxy(code) wraps the user expression in a page-side Proxy that throws [secure_eval] errors when blocked APIs are touched at runtime. The wrapped code is passed with prewrapped: true so the extension knows not to wrap again.
Disable only at extreme cost Operators can opt out via SUPERSURF_DISABLE_SECURE_EVAL=1 or --disable-secure-eval. This removes the only RCE protection in front of browser_evaluate — agent prompt injection becomes a path to arbitrary page-context JS. See Trust Boundaries & Security for the full threat model and defense layering.
Function form { function: '() => 42' } is wrapped as (() => 42)() before evaluation (browser_evaluate/index.ts:42). Without the IIFE wrap, an arrow function literal returns undefined because the result of a bare function expression is the function itself, not its return value.

page_diffing side-effect on browser_interact

No dedicated tool. Behavior change: when enabled, browser_interact captures a DOM snapshot before the first action and after the last, then appends a diff section to the response (experimental/page-diffing.ts). The diff includes added / removed text, element-count delta, and per-form-field { field, from, to } changes. Confidence scoring penalizes shadow-DOM-heavy pages, multi-iframe pages, and very large pages. Confidence below 0.5 returns "full re-read recommended" instead of the raw diff (interaction/index.ts:84-89).

smart_waiting side-effect on navigation/click

No dedicated tool. Behavior change: browser_navigate and the click action call ext.sendCmd('waitForReady') after the action, polling DOM mutation rate until it stays below threshold for stabilityMs (500–3000 depending on caller) instead of relying on a fixed delay. See navigation.ts:78-128 and interaction/click.ts:40-43.

mouse_humanization side-effect on cursor moves

No dedicated tool. Behavior change: cursor movement before clicks and hovers follows a Bézier-curve waypoint path with random personality traits (speed, overshoot tendency, curvature, jitter) drawn from the Balabit Mouse Dynamics dataset distribution. Per-session state in experimental/mouse-humanization/index.ts:42-66; path generation in experimental/mouse-humanization/generator.ts. The DistributionProfile interface (profile.ts) is the swap point for BeCAPTCHA-trained profiles when the dataset is available.
