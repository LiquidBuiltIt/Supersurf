Server Core

The MCP server is the supersurf-mcp npm package. One process per AI client. Owns the MCP stdio transport, the connection state machine, the Unix-socket transport to the daemon, the always-on audit trail, and a number of small but load-bearing utilities (tips, dotenv, script mode, logging). This page covers everything in server/src/ except the browser tool handlers themselves — those live in Browser Tools.

1. Overview & process role

The MCP server's job is narrow: translate MCP tool calls from the agent into JSON-RPC commands that get forwarded to the daemon, write an audit log entry for every call, and prepend a status header to every response so the agent can see at a glance what state the connection is in.

It does not own the WebSocket to the extension — the daemon does that. Any number of MCP server processes can attach to the same daemon, each with its own session ID and tab ownership.

The whole module surface is a thin layer plus three pieces of real logic:

2.3 The exit-code-42 hot reload

This is the cleverest piece of the file and worth understanding because it is the only reason npm run dev.server looks transparent to the MCP client. The flow at cli.ts:63-118:

  1. Parent process is started with --debug and no --child flag.
  2. Two PassThrough streams sit between the MCP client's real stdin/stdout and whatever child process is running: 
    process.stdin.pipe(inputBuffer);
outputBuffer.pipe(process.stdout);
  3. The wrapper spawns the same script with --child appended and pipes inputBuffer → child.stdin and child.stdout → outputBuffer (with { end: false } so the wrapper's stdout doesn't close when the child exits).
  4. On child.exit, the pipes are unpipped. If the exit code is 42, the wrapper waits 100 ms and respawns. Any other code propagates up and the wrapper exits.

The reload_mcp tool (debug only) is what triggers exit 42 from inside the child: setTimeout(() => process.exit(42), 100) (backend/handlers.ts:601, 605). The 100 ms grace lets the MCP response flush over stdio before the child dies.

Why PassThrough buffers? The MCP client opened one stdio connection. If the wrapper let process.stdin connect directly to child.stdin and the child died, the parent's stdin would block and the next child wouldn't receive subsequent messages. The buffers decouple the lifetimes — the MCP client sees one continuous connection across N reloads.

2.4 main() boot sequence

main(options) at cli.ts:163 does the following in order:

  1. loadDotenv(process.cwd()) — before anything else reads process.env.
  2. Sets global.DEBUG_MODE from the parsed debug mode.
  3. Initializes LoggerRegistry debug mode.
  4. Builds BackendConfig via resolveConfig() (cli.ts:40-55) — this reads SUPERSURF_EXPERIMENTS from the environment and stores it on the config.
  5. Constructs ConnectionManager (passive state).
  6. Creates an MCP Server with capabilities { tools: {}, logging: {} }.
  7. Wires ListToolsRequestSchema and CallToolRequestSchema to backend.listTools() / backend.callTool().
  8. setupExitWatchdog() (cli.ts:124-157) wires SIGINT, SIGTERM, and process.stdin.close to a single cleanup that calls backend.serverClosed() + server.close(). Force-exits after 5 s if cleanup hangs.
  9. Connects StdioServerTransport — ready.

Note: there is no idle timeout on the server (comment at cli.ts:159). The connection stays alive until the agent disconnects or the daemon (10-minute idle) shuts itself down.

3. Connection state machine

ConnectionManager at backend.ts:52 owns the state machine and dispatch table. The three states:

StateMeaningTools available
passive Server booted, no daemon connection. Connection tools (connect, disconnect, status, experimental_features) + profile tools (profile_*) + browser tool schemas only.
active Daemon socket connected, browser may or may not be linked. All of the above. Browser tools start to actually work as the extension reports tab attachments.
connected Extension reported a tab via onTabInfoUpdate. Full tool surface.

3.1 Lazy import to break the cycle

tools.ts imports types from backend.ts. So backend.ts cannot statically import tools.ts. The fix is a one-liner pattern at backend.ts:36-46:

let BrowserBridge: any = null;
async function getBrowserBridge(): Promise<any> {
  if (!BrowserBridge) {
    const mod = await import('./tools');
    BrowserBridge = mod.BrowserBridge;
  }
  return BrowserBridge;
}

The same pattern is repeated inside backend/handlers.ts:27-35 because handlers also need to construct a BrowserBridge at connect time.

3.2 listTools()

listTools() (backend.ts:98-116) returns the union of:

  • Connection tool schemas from getConnectionToolSchemas() (backend/schemas.ts:17).
  • Browser tool schemas from a dummy BrowserBridge instance (one with a null transport — schemas don't need a live connection).
  • Profile tool schemas from getProfileToolSchemas() (backend/schemas.ts:98).
  • reload_mcp if --debug is on.

So even in passive state the agent sees the full tool list. Calls to browser tools before connect are caught at backend.ts:226-243 and return a textual “Browser Automation Not Active” error.

3.3 callTool() dispatch

The dispatch path at backend.ts:125-246:

  1. Tool name is checked against a fixed BACKEND_TOOLS set (backend.ts:134-137): 
    ['connect', 'disconnect', 'status', 'experimental_features',
 'reload_mcp', 'profile_create', 'profile_list', 'profile_delete']
  2. If connect is being called and there is no auditLogger yet, one is constructed using the client_id argument (backend.ts:141-143). This means the connect call itself is audited.
  3. Backend tools are dispatched via a switch to functions in backend/handlers.ts.
  4. The result/error is audit-logged with duration, URL, error message, and (for connect) MCP client info.
  5. Anything that's not a backend tool is forwarded to this.bridge.callTool(...) — the lazy-loaded BrowserBridge.

3.4 Status header

Every MCP-mode response is prepended with a one-line status header from buildStatusHeader() (backend/status.ts:30). It is a pure function — no side effects, all state passed in. Examples:

🔴 v1.11.0 | Disabled
---

✅ v1.11.0 | 🌐 chrome | 📄 Tab 1: https://example.com | 🔧 React, Vue
---

✅ v1.11.0 [14:32:08] | 🌐 chrome | ⚠️ No tab attached | 🕵️ Stealth
---

Build timestamp ([14:32:08]) only shows in debug mode. URLs longer than 50 chars get truncated to 47 + ... (backend/status.ts:62-63). The trailing \n---\n\n is markdown separator hygiene so the body that follows isn't glued to the header.

4.2 Profile tool handlers

Profile tools (profile_create, profile_list, profile_delete) are special: they need to talk to the daemon even when the session is in passive state. The pattern at handlers.ts:443-468 is withDaemonConnection():

  • If mgr.extensionServer already exists (the session is connected), reuse it.
  • Otherwise ensureDaemon() + spin up a temporary DaemonClient (with a synthetic session ID profile-mgmt-<timestamp>) for the duration of the call, then close it.

Each profile handler also calls checkProfileCapability() (handlers.ts:471) which gates on client.capabilities.profiles. If profiles aren't enabled on the daemon, returns a “Profile management is not enabled” error pointing the user at SUPERSURF_EXPERIMENTS=profiles.

4.3 Tool schemas worth knowing

From backend/schemas.ts:

  • connect requires client_id, optionally takes profile for managed Chromium binding (schemas.ts:19-45).
  • experimental_features exposes only the four session-toggleable experiments — page_diffing, smart_waiting, storage_inspection, mouse_humanization (schemas.ts:71-94). profiles is intentionally omitted because it is a daemon-startup-only flag.
  • reload_mcp is annotated destructiveHint: true and only listed when debugMode is true (schemas.ts:163-176, gated at backend.ts:108-111).

5. Daemon transport & spawning

Two files, both small.

5.1 daemon-spawn.ts

FunctionLineBehavior
getSockPath()daemon-spawn.ts:24Returns ~/.supersurf/daemon.sock.
getPidPath()daemon-spawn.ts:29Returns ~/.supersurf/daemon.pid.
isDaemonRunning()daemon-spawn.ts:47Reads PID file, calls process.kill(pid, 0) as a liveness probe.
ensureDaemon(port, debug, experiments)daemon-spawn.ts:66If not running: clean stale files, ensure dir, spawn detached, poll for socket.

The “clean stale files” step at daemon-spawn.ts:75-76 is what saves a developer who SIGKILLed the daemon — the next connect call clears the leftover PID and socket files before respawning.

Why a login shell to spawn the daemon? daemon-spawn.ts:103-115 spawns the daemon via spawn(SHELL, ['-ilc', cmd]) instead of spawn(daemon, args). The reason is environment inheritance: GUI MCP clients (Claude Desktop, IDEs) don't source ~/.zshrc / ~/.bashrc, so any SUPERSURF_EXPERIMENTS=profiles the user set there isn't in process.env. The login shell sources rc files, picks up the env vars, and passes them through.

Daemon resolution at daemon-spawn.ts:84-96 tries require.resolve('supersurf-daemon/dist/main.js') first, then falls back to npx supersurf-daemon@latest. So a globally installed npm package wins over npx.

Polling waits up to 10 s with 100 ms intervals (daemon-spawn.ts:120-134); throws on timeout.

5.2 daemon-client.ts

DaemonClient at daemon-client.ts:28 implements the IExtensionTransport interface defined in bridge.ts:28-38. It looks like the WebSocket-based ExtensionServer from the outside, but speaks NDJSON over a Unix socket to the daemon.

Handshake

start() at daemon-client.ts:67-155 opens a net.createConnection(sockPath), sends:

{ "type": "session_register", "sessionId": "<clientId>" }\n

Then waits for one of:

{ "type": "session_ack", "browser": "chrome", "buildTimestamp": "...",
  "capabilities": { "profiles": true } }\n
{ "type": "session_reject", "reason": "..." }\n

The capabilities object is parsed at daemon-client.ts:105 and exposed via the capabilities getter (daemon-client.ts:59-61). onConnect reads it back at handlers.ts:149 and stores it on the ConnectionManager — that's what the profile capability check uses.

Connection timeout is 10 s (daemon-client.ts:73-76); longer than that and start() rejects.

Steady state

After ack, the buffer-and-split loop at daemon-client.ts:87-138 reads lines off the socket. Each line is parsed as JSON. JSON-RPC responses with a numeric/string id are looked up in this.inflight and the corresponding promise resolves or rejects.

One side trick: if the result has a currentTab field (daemon-client.ts:128-130), it's passed to onTabInfoUpdate. This is how navigation/snapshot results silently update the attached tab metadata in the status header without a separate tab-info RPC.

sendCmd

sendCmd(method, params, timeout) at daemon-client.ts:160-190:

  • Throws if not connected.
  • Generates an 8-char request ID via crypto.randomUUID().slice(0, 8).
  • Stores resolve/reject in the inflight map.
  • Default timeout is 60 s; the server passes longer values for slow calls (e.g. 90 s for profiles.connect at handlers.ts:154).

On socket close, drainInflight() (daemon-client.ts:213-220) rejects every pending request with “Daemon connection closed”.

notifyClientId() is a no-op (daemon-client.ts:193-195) — the daemon owns extension authentication so the server doesn't need to send a separate notification.

6. Audit logging

Audit logging is always on, not gated behind --debug. This is deliberate: the audit trail is supposed to be a forensic record of what an agent did with this machine, useful both for debugging and for after-the-fact accountability.

AuditLogger lives at audit-logger.ts:55-79.

6.1 File location and naming

One file per session, written under ~/.supersurf/logs/sessions/:

audit-{sessionId}-{ISO_timestamp}.ndjson

Construction is at audit-logger.ts:58-64:

const ts = new Date().toISOString().replace(/[:.]/g, '-');
const safe = sessionId.replace(/[^a-zA-Z0-9_-]/g, '_');
this._path = path.join(dir, `audit-${safe}-${ts}.ndjson`);

Both the timestamp and the session ID are sanitized so weird client IDs (e.g. with slashes) can't escape the directory.

6.2 NDJSON entry shape

One JSON object per line. The AuditEntry interface (audit-logger.ts:40-53):

interface AuditEntry {
  ts: string;                            // ISO 8601, set by write()
  version: string;                       // pkg.version of supersurf-mcp
  session_id: string;
  tool: string;
  params: Record<string, unknown>;       // redacted
  result: 'ok' | 'error';
  error?: string;
  url?: string;                          // current attached tab URL
  duration_ms: number;
  tip?: string;                          // matched tip message, if any
  client?: { name: string; version: string };  // MCP client info, on connect only
  experiments?: Record<string, boolean>;
}

6.3 Redaction rules

redactParams() at audit-logger.ts:30-38 is what makes the audit log safe to share:

RuleKeys (case-insensitive)Behavior
Redactedvalue, password, token, secret, credentialReplaced with the literal string "[REDACTED]".
StrippeddataKey is omitted entirely (this is where screenshot base64 blobs would go).
What redaction does not catch Match is on top-level key name only. A { args: { password: "..." } } shape would not have the inner password redacted — the redaction loop walks one level. Tool input schemas are flat by design, but this is a footgun if you change a schema. The audit-logger tests at server/tests/audit-logger.test.ts exercise the top-level cases.

6.4 Where it's called from

The AuditLogger is constructed lazily on the first connect call (backend.ts:141-143) and reused for the lifetime of the session. Two write sites:

  • Backend tools: backend.ts:174-198 on success, backend.ts:201-220 on thrown error.
  • Browser tools: written from inside BrowserBridge — see Browser Tools.

7. Tips registry

tips.ts is a contextual hint engine. Every tool response can be checked against ~14 hand-written rules; if a rule matches, its message gets appended to the response. The point is to nudge agents off anti-patterns — mostly using browser_evaluate for things that have a purpose-built tool.

7.1 Rule shape

TipRule at tips.ts:11-17:

interface TipRule {
  id: string;
  priority: number;                     // lower = higher priority
  tool: string;                         // exact tool name match
  match: (params, result, error) => boolean;
  message: string;
}

The registry TIPS at tips.ts:51-210 has rules for:

  • browser_evaluate + .click() → use browser_interact.
  • browser_evaluate + dispatchEvent → CDP synthetic detection warning.
  • browser_evaluate + scroll/value/focus/location/querySelector/innerHTML/getBoundingClientRect/getComputedStyle → respective dedicated tools.
  • browser_interact errors: no tab attached, not a <select>, element not found.
  • browser_take_screenshot → reminder that screenshot: true works inline on other actions.

7.2 Priority resolution

getTip() at tips.ts:212-253 walks all rules bound to this tool, collects matches, then returns the message of the lowest-priority-number match. Ties are broken in registry order.

7.3 Suppression after 3 consecutive fires

To avoid nagging the same agent with the same tip forever, there's a per-session, per-tip counter. The constant SUPPRESS_AFTER = 3 at tips.ts:20:

  • For every tool call with a session ID, every tip rule bound to this tool either increments its counter (if it matched) or resets it to 0 (tips.ts:237-247).
  • If the winning tip's counter is > 3, the tip is suppressed and getTip returns null (tips.ts:250-251).
  • Per-tip reset means tip A firing doesn't reset tip B's counter.

clearTipCounters(sessionId) at tips.ts:34-36 is called from onDisconnect (handlers.ts:265) so a reconnect starts fresh.

Without a session ID (e.g., in unit tests), getTip behaves as a pure function with no suppression (tips.ts:233).

8. Dotenv loader for secure_fill

dotenv.ts is a 49-line minimal .env reader. Three reasons it exists despite the npm dotenv package being trivially installable:

  1. The server has a hard “zero deps that don't earn their weight” rule.
  2. It needs a side feature: tracking which keys came from the .env file specifically, separate from the rest of process.env.
  3. That tracking powers secure_fill's credential discovery UI (the agent gets to see names of available env vars without ever seeing their values).

8.1 API

FunctionLineBehavior
loadDotenv(dir)dotenv.ts:23Reads <dir>/.env. Splits on =, strips matching surrounding quotes (single or double), skips comments and blanks. Sets process.env[key] only if it's currently undefined — existing env vars win.
getDotenvKeys()dotenv.ts:15Returns the array of key names that were seen in the .env file. Values are never exposed.
Trust boundary The agent calls secure_fill with an env var name, never a value. The server resolves the name against process.env, types it char-by-char into the page via the extension, and never returns the cleartext to the agent. getDotenvKeys() is the discovery half — tells the agent what names are available without giving away anything else.

Called once early in cli.ts:165 (and again in script-mode startup at cli.ts:244), before anything else reads process.env.

9. Script mode

--script-mode bypasses MCP entirely and serves plain JSON-RPC 2.0 over stdio. Used by shell scripts and integration tests that don't want the MCP framing tax.

Entry point is startScriptMode(config) at stdio.ts:19-70. It:

  1. Constructs a ConnectionManager and calls initialize(null, {}) — passing null for the MCP Server instance because there isn't one.
  2. Sets up readline on stdin, line-buffered, no terminal.
  3. For each line: parse JSON, pass to handleRequest(). Single objects become single responses; arrays are batched and resolved concurrently with Promise.all.
  4. Wires SIGINT/SIGTERM/rl.close to a graceful backend.serverClosed() + process.exit(0).

9.1 handleRequest()

At stdio.ts:77-109. JSON-RPC 2.0 validation:

ConditionError code
Parse error (top of file)-32700
jsonrpc !== '2.0'-32600
Missing or non-string method-32600

The crucial difference from MCP mode: tools are dispatched with { rawResult: true } (stdio.ts:100). That option trickles all the way through backend.ts:128 and the handlers in backend/handlers.ts which check options.rawResult at every response site — returning plain JSON objects (e.g. { success: true, state: 'active' }) instead of MCP content wrappers.

11. Legacy ExtensionServer (bridge.ts)

bridge.ts is the pre-daemon transport. Before the multiplexer was added, the MCP server itself ran the WebSocket on 127.0.0.1:5555 and the extension connected directly to it. This still works, but the live path now goes through DaemonClient.

The file is kept for two reasons:

  1. The IExtensionTransport interface (bridge.ts:28-38) is the contract DaemonClient implements. Both transports are drop-in replacements for each other.
  2. Tests cover it directly (server/tests/bridge.test.ts) — easier than mocking a full daemon.

11.1 IExtensionTransport interface

interface IExtensionTransport {
  sendCmd(method, params?, timeout?): Promise<any>;
  readonly connected: boolean;
  readonly browser: string;
  readonly buildTime: string | null;
  onReconnect: (() => void) | null;
  onTabInfoUpdate: ((tabInfo: any) => void) | null;
  notifyClientId(clientId: string): void;
  start(): Promise<void>;
  stop(): Promise<void>;
}

The daemon-aware DaemonClient (§5.2) and the legacy ExtensionServer both implement this. Anything in the codebase that takes an IExtensionTransport works with either.

11.2 What ExtensionServer does

ExtensionServer at bridge.ts:50:

  • Spins up http.createServer on 127.0.0.1:5555 (default) plus a WebSocketServer attached to it (bridge.ts:83-90).
  • Single-connection model: rejects additional clients with JSON-RPC error -32001 "Another browser is already connected. Only one browser at a time." and closes after 100 ms with WebSocket code 1008 (bridge.ts:106-119).
  • 10 s ping keep-alive (bridge.ts:138-142).
  • Three message kinds in handleMessage() (bridge.ts:177-225): JSON-RPC responses correlated by id, handshakes (type: 'handshake' populating browserType/buildTimestamp), and tab info notifications (method === 'notifications/tab_info_update').
  • Same currentTab piggyback as DaemonClient (bridge.ts:188-191).
  • onRawConnection hook (bridge.ts:63) is the escape hatch the daemon uses to take over connection handling for the profile pool.
Why the daemon won Single-connection broke down once we wanted > 1 MCP session per machine (multiple agents, parallel scrapes). The daemon is what lets a single WebSocket be shared with tab-ownership enforcement. The server retains ExtensionServer only as the contract surface and a test fixture.

TL;DR
The server is a thin MCP-to-daemon translator. Its only real moving parts are a three-state connection machine (backend.ts), a Unix-socket transport (daemon-client.ts) with a session handshake that carries capabilities, an always-on audit log with key-name-only redaction (audit-logger.ts), a tip engine that nudges agents off browser_evaluate spirals (tips.ts), and a clever exit-code-42 hot reload trick that keeps --debug transparent to the MCP client (cli.ts). Every other file is plumbing.
Source of truth: server/src/ in the repo.
