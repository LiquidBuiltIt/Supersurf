System Architecture

SuperSurf is an MCP server that gives any AI agent control of a real Chrome browser. The defining bet: drive Chrome through a sideloaded extension instead of through CDP, trading ~50 protocol domains for stealth and a real, lived-in browser profile.

1. What SuperSurf is

SuperSurf is an open-source MCP server that gives any AI agent control of a real Chrome browser. It is published on npm as supersurf-mcp and on the Chrome Web Store as the SuperSurf extension. Apache-2.0 with a Commons Clause; owned by The Media Masons / LiquidBuilt.

The product is structured around one core thesis: agents that drive a browser through CDP (Puppeteer, Playwright, Selenium-WebDriver) leak in ways anti-bot vendors fingerprint — navigator.webdriver, VM-instance artifacts from Runtime.evaluate, sterile profiles, missing extensions, predictable DOM mutation patterns. SuperSurf instead drives Chrome through a sideloaded extension whose content scripts run in an isolated world that page JavaScript cannot observe. The agent operates inside the user's real browser profile (cookies, history, localStorage, installed extensions), and the presence of the extension itself is a positive human signal to anti-bot systems.

The research basis lives in knowledge/chat/supersurf-browser-automation.md. Key facts:

  • The classic CDP detection signal (Runtime.enable) was patched in V8 in May 2025 — anti-bot vendors moved on to behavioral fingerprinting (mouse, scroll, timing, network).
  • Chrome 136+ requires a separate --user-data-dir for remote debugging, so raw CDP cannot use a real profile anyway.
  • Raw CDP exposes ~80 protocol domains; chrome.debugger (the extension wrapper) exposes ~27 plus a debugger infobar. SuperSurf trades that surface area for stealth and real-profile access.

Every line of server and extension code is published; there is no obfuscated binary, no telemetry.

2. The four-process architecture

┌───────────┐ stdio (MCP) ┌─────────────┐ Unix socket ┌──────────┐ WebSocket (JSON-RPC 2.0) ┌──────────────────┐ │ AI Agent │ ─────────────▶ │ MCP Server │ ──(NDJSON)────▶ │ Daemon │ ─────────────────────────▶ │ Chrome Extension │ │ (Claude, │ │ (Node.js) │ │ (Node.js)│ │ (MV3 SW + │ │ GPT, etc) │ │ supersurf- │ │ supersurf│ │ content │ │ │ │ mcp │ │ daemon │ │ scripts) │ └───────────┘ └─────────────┘ └──────────┘ └──────────────────┘ │ │ Chrome APIs / CDP ▼ ┌──────────────────┐ │ Browser Tabs │ │ (DOM, network) │ └──────────────────┘

2.1 AI Agent → MCP Server (stdio + MCP)

The MCP server is the npm-published supersurf-mcp package. Its entry point is server/src/cli.ts which wires up @modelcontextprotocol/sdk's Server over StdioServerTransport. Tool listing and tool dispatch are forwarded to the ConnectionManager defined in server/src/backend.ts:52.

Two alternative transports exist:

  • --script-mode (server/src/stdio.ts) skips MCP framing entirely and exposes JSON-RPC 2.0 over stdio for shell-script automation.
  • --debug runs the server as a wrapper that forks itself with --child, piping stdin/stdout through PassThrough streams so a child exit code of 42 triggers a hot reload without disconnecting the MCP client (server/src/cli.ts:63).

2.2 MCP Server → Daemon (Unix domain socket, NDJSON)

The MCP server does not own the extension WebSocket. Instead, on connect it spawns or joins a long-lived daemon process via ensureDaemon() in server/src/daemon-spawn.ts:66, and connects through a Unix domain socket at ~/.supersurf/daemon.sock.

The transport is line-delimited NDJSON. The handshake (session_register → session_ack) is implemented in server/src/daemon-client.ts. After the handshake, the server forwards JSON-RPC 2.0 over the same socket. The session_ack payload also carries capabilities: { profiles: boolean } so the server knows whether to expose profile management tools.

2.3 Daemon → Chrome Extension (WebSocket, JSON-RPC 2.0)

The daemon is the npm-published supersurf-daemon package. It runs a WebSocket server on 127.0.0.1:5555 (configurable via --port) inside daemon/src/extension-bridge.ts. The extension auto-connects from its service worker (extension/src/connection/websocket.ts).

The wire protocol is JSON-RPC 2.0. The daemon uses a RequestScheduler (daemon/src/scheduler.ts) to enforce round-robin fairness, tab ownership, and auto context-switching when more than one MCP session is connected. With the profiles experiment enabled, the daemon swaps a single-connection bridge for a Matchmaker (daemon/src/profiles/matchmaker.ts) that pools multiple Chromium instances and routes commands by profile name.

2.4 Extension → Browser

The extension is MV3 (extension/manifest.json). It uses:

  • Content scripts (extension/src/content-script.ts, registered for <all_urls> at document_start, all_frames: false) for DOM reads/writes — in an isolated world page JS cannot detect.
  • chrome.debugger (CDP through the extension wrapper) only for screenshots, network interception, PDF generation.
  • Standard Chrome APIs for tabs, downloads, storage, alarms, webRequest, webNavigation, scripting, tabGroups, cookies, management.

This split is the system's defining design choice — see Section 7.

3. Connection lifecycle

The ConnectionManager in server/src/backend.ts:52 is a three-state machine:

StateMeaningTools available
passive Server booted, MCP transport open, no daemon connection. connect, disconnect, status, experimental_features, profile_* (when daemon supports it)
active Daemon socket connected, waiting for the extension to register. All of the above
connected Extension is alive on the daemon side, tab is attached. All ~30+ browser tools

Boot path

MCP client launches npx supersurf-mcp → server enters passive (backend.ts:54). The MCP ListTools handler returns connection tools + browser tool schemas (lazily loaded via getBrowserBridge() in backend.ts:40) so the agent sees the full tool list immediately, but calls to browser tools error with “Browser Automation Not Active” until connect is invoked (backend.ts:226-243).

connect path

The onConnect handler in server/src/backend/handlers.ts calls ensureDaemon(). If no daemon is running it spawns one via a login shell (so SUPERSURF_EXPERIMENTS from ~/.zshrc is inherited — see daemon-spawn.ts:103-117), then polls for the socket file with a 10s timeout. Once connected, the server transitions to active and constructs a BrowserBridge (server/src/tools.ts) over the daemon transport. When the extension reports a tab attachment via onTabInfoUpdate, the state advances to connected.

Multi-session multiplexing

A single daemon owns one WebSocket to the extension and serves all MCP sessions on this machine. Each session gets its own Unix-socket connection, a sessionId, optional tab ownership, and (in profiles mode) an optional profileId binding. The scheduler arbitrates; tab ownership prevents two sessions from stomping each other's tabs.

Idle & shutdown

The daemon resets a 10-minute idle timer whenever a session disconnects; if the count reaches zero and stays zero, the daemon SIGTERMs itself (daemon/src/main.ts:444-450). The MCP server has no idle timeout — it stays alive until the agent disconnects. On shutdown the daemon also SIGTERMs any managed Chromium processes from the profiles experiment (main.ts:464-485).

4. Build system

The repository is an npm workspace monorepo (package.json:7):

shared/      — zero-runtime-dep utilities, imported by both daemon and server
daemon/      — supersurf-daemon (published)
server/      — supersurf-mcp     (published)
extension/   — Chrome extension  (CWS + zipped releases)

Build order is enforced because server and daemon both depend on shared, and the server's dependencies include supersurf-daemon: "*" (workspace-resolved during dev, npm-resolved at install time):

npm run build           # = build.shared && build.daemon && build.server && build.extension

Each subpackage's build runs tsc then npx tsx ../scripts/shared.bundle.ts <pkg> to inline the workspace-only shared package into the published artifact (so consumers don't need to install a private package).

Dev loop

npm run dev.server      # tsx server/src/cli.ts --debug    (hot-reload via wrapper)
cd extension && npm run dev   # tsc --watch
npm run test            # daemon + server + extension Vitest suites
npm run filesize        # line counts across the four packages

Versioning

Versions are kept in lockstep across package.json, server/package.json, daemon/package.json, extension/package.json, extension/manifest.json, and shared/package.json. The script scripts/version.bump.ts rewrites all six files atomically and creates a single commit v<X.Y.Z> — <message>. It deliberately does not create a git tag — tagging is reserved for npm run publish, so unreleased bumps don't pollute the tag namespace. A rollback subcommand undoes the most recent unpushed bump.

Publish pipeline

scripts/publish.ts is a single command that owns the full release:

  1. Pre-flight — verify .cws-token, refresh-token validity, clean working tree, HEAD is a vX.Y.Z commit, all six version files match.
  2. GitHub — create the vX.Y.Z tag (idempotent), git push && git push --tags. Deletes the local tag on push failure for clean retries.
  3. npm — publish daemon first (server depends on it), then server. Each subpackage's prepublishOnly re-runs clean && build and copies the root LICENSE in.
  4. Chrome Web Store — build the extension, zip manifest.json + dist/ + assets/, OAuth refresh against Google's CWS API, upload, publish.

Failures are recorded per-step and the summary tells you the exact remediation command (cd daemon && npm publish, npm run cws.publish, etc.).

6. On-disk layout

Everything lives under ~/.supersurf/:

~/.supersurf/
├── daemon.pid                    # PID of the running daemon
├── daemon.sock                   # Unix socket — server↔daemon IPC
├── logs/
│   ├── daemon.log                # always-on for core events; verbose with --debug
│   ├── server.log                # MCP server log (debug-mode only)
│   └── sessions/
│       ├── supersurf-debug-{client_id}-{timestamp}.log    # per-session debug
│       └── audit-{sessionId}-{timestamp}.ndjson           # always-on audit trail
├── extension/                    # cached extension (profiles experiment)
├── daemon/                       # daemon-internal scratch (profiles only)
└── profiles/
    └── <profile-name>/
        └── chrome-data/          # Chromium --user-data-dir per profile

Constants are defined at daemon/src/main.ts:37-41 and server/src/daemon-spawn.ts:19-21. The audit logger is at server/src/audit-logger.ts; it writes NDJSON for every tool call with redacted value / password / token / secret / credential fields and stripped data blobs (screenshots).

Sandbox note ~/.supersurf/ is not sandbox-writable in many development setups. A literal ~/ directory will appear at the project root if you write under ~/.supersurf/ from inside a sandboxed shell. Treat the path as read-only from sandbox sessions.

7. Design principles

These come straight from CLAUDE.md's Design Principles section and are load-bearing — they constrain almost every decision.

Content-script-first for DOM interaction

All DOM reads/writes go through content scripts in the isolated world. CDP (chrome.debugger) is reserved for screenshots, network interception, and PDF generation only. CDP-injected scripts appear as VM instances in V8 memory profiling; content scripts in the isolated world are invisible to page JavaScript. This is a deliberate anti-bot posture.

Auto-fallback iframe resolution

Selector-based actions (browser_interact, browser_fill_form) try the top frame first, then DFS-walk child frames via Page.createIsolatedWorld if the element isn't found. See server/src/tools/frames.ts. Rationale: humans don't think about frames, and iframe-nested elements were causing agents to thrash with browser_evaluate spirals. The frame helpers also walk the iframe tree to convert iframe-local coords to top-frame viewport coords for click humanization.

Extension over raw CDP

Sacrifices ~50 CDP domains in exchange for: real browser profile (cookies, history, localStorage, installed extensions), no detectable launch flags, no --user-data-dir requirement on Chrome 136+, sideload-friendly CI (chrome --load-extension=...), and the extension itself as a positive fingerprint signal. The codebase is explicit that this tradeoff is the central design bet.

Lazy import to break cycles

backend.ts lazy-imports tools.ts (backend.ts:37-46) because tools.ts imports types from backend.ts. Worth knowing because new contributors hit this pattern often.

Deferred work (intentionally not built)

  • Dataset-driven mouse profiles — the DistributionProfile interface is wired up so hand-tuned Balabit constants can be swapped for BeCAPTCHA-trained profiles when dataset access arrives.
  • Cloud relay, OAuth, multi-browser switching, shared access — all explicitly out of scope.

8. Platform support & dependencies

Platforms: macOS and Linux only. Windows is explicitly unsupported in server/package.json:18-21 and daemon/package.json:19-22 ("os": ["darwin", "linux"]).

Node.js: ≥18.

Runtime dependencies:

  • shared/ — zero runtime deps. Node built-ins only (fs, path, os).
  • daemon/ — ws only.
  • server/ — @modelcontextprotocol/sdk, acorn + acorn-walk (AST analyzer for secure_eval), commander, ws, sharp, image-size, jsonpath-plus, plus the workspace supersurf-daemon and shared.
  • extension/ — zero runtime deps. Browser APIs only.

External requirements: Chrome or Chromium installed locally; an MCP-aware client (Claude Code, Claude Desktop, etc.). The extension can be installed from the Chrome Web Store (extension ID falcdhojcinkkbffgnipppcdoaehgpek) or sideloaded with --load-extension=./extension --user-data-dir=....

TL;DR
Four-process, MCP-native browser automation. MCP server runs on stdio, talks Unix-socket NDJSON to a long-lived multiplexer daemon, which talks WebSocket JSON-RPC to a sideloaded MV3 extension, which uses content scripts in an isolated world for DOM work and chrome.debugger only for screenshots / network / PDF. Optimized for stealth and a real, lived-in browser profile rather than for raw protocol surface area.
