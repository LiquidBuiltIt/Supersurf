Daemon

The standalone coordinator process. Owns the single Chrome extension WebSocket (or pool of them when profiles are enabled) and multiplexes JSON-RPC tool calls from any number of MCP server sessions. This is what lets multiple agents share one browser without stepping on each other's tabs.

MCP servers (N) ──Unix socket──▶ Daemon ──WebSocket(:5555)──▶ Chrome extension(s) │ ├─ SessionRegistry (per-session tab ownership) ├─ RequestScheduler (round-robin queue) ├─ ExtensionBridge + Matchmaker (connection pool) ├─ ProfileRegistry (managed Chromium profiles) └─ DaemonExperimentRegistry (per-session experiments)

All daemon source lives in daemon/src/. The package (supersurf-daemon) depends only on ws and the workspace-local shared package.

1. Entry point and process lifecycle

The shebang-prefixed daemon/src/main.ts is the daemon binary. It handles CLI parsing, PID/socket file management, idle timeout, signal handling, and wiring up every other subsystem.

Filesystem layout

The daemon owns ~/.supersurf/:

PathPurpose
~/.supersurf/daemon.pidPID of the running daemon. Used for liveness checks and stop.
~/.supersurf/daemon.sockUnix domain socket — IPC entry point for MCP servers.
~/.supersurf/logs/daemon.logAlways-on FileLogger output.
~/.supersurf/daemon/managed-pids.jsonlAppend-only spawn/kill log for orphan recovery.
~/.supersurf/profiles/<name>/Per-profile data dir (only when profiles enabled).
~/.supersurf/extension/Cached extension bundle for managed Chromium.

Constants are defined at daemon/src/main.ts:37-41:

const SUPERSURF_DIR = path.join(os.homedir(), '.supersurf');
const PID_FILE      = path.join(SUPERSURF_DIR, 'daemon.pid');
const SOCK_FILE     = path.join(SUPERSURF_DIR, 'daemon.sock');
const LOG_FILE      = path.join(SUPERSURF_DIR, 'logs', 'daemon.log');
const IDLE_TIMEOUT_MS = 10 * 60 * 1000; // 10 minutes

CLI subcommands

SubcommandBehavior
start (default)Self-daemonize: re-spawn detached and exit parent.
stopSIGTERM the PID, escalate to SIGKILL after 5s, clean up files.
restartstopDaemon() then start fresh.
status [--verbose]Connect to socket and pretty-print daemon state.
observetail -f the daemon log file.

Self-daemonization is implemented by daemonize() (daemon/src/main.ts:532): re-spawn process.execPath __filename ...args --_daemonized with detached: true, stdio: 'ignore', then child.unref() and process.exit(0). The --_daemonized flag tells the child to actually run main() instead of forking again.

PID file management

writePidFile(), cleanStaleFiles(), cleanupFiles(), and isProcessAlive() (daemon/src/main.ts:287-327) handle the lifecycle. isProcessAlive(pid) uses the process.kill(pid, 0) no-op signal trick. On startup the daemon:

  1. Ensures ~/.supersurf/ exists.
  2. Calls cleanStaleFiles() to remove PID/sock files left by a crashed previous instance.
  3. If a PID file points at a live process, prints “Daemon already running” and exits with code 1.
  4. Otherwise writes its own PID to PID_FILE.

Idle timeout

A single idleTimer (daemon/src/main.ts:435-450) fires after 10 minutes with no sessions:

ipc.setSessionCountCallback((count: number) => {
  if (count === 0) startIdleTimer();
  else resetIdleTimer();
});

When the timer fires, shutdown() is called.

Signal handlers and graceful shutdown

SIGTERM and SIGINT are both wired to the same async shutdown() (daemon/src/main.ts:464). The shuttingDown flag prevents re-entry. shutdown():

  1. Cancels the idle timer.
  2. If profiles are enabled, iterates every profile in ProfileRegistry, sends SIGTERM to its running PID (if any), and writes a kill entry to managed-pids.jsonl.
  3. Calls scheduler.drainAll() to reject every queued request with “Daemon shutting down”.
  4. Awaits ipc.stop() and bridge.stop().
  5. Calls cleanupFiles() to remove PID and socket files.
  6. process.exit(0).

Note: there is no explicit SIGHUP handler — only SIGTERM/SIGINT.

Spawning from the server

The server's daemon-spawn.ts calls ensureDaemon(), which checks isDaemonRunning() (PID file + liveness probe). If the daemon isn't up, it spawns the npm-linked supersurf-daemon binary and polls for the socket file. The first server to call connect brings the daemon up; subsequent servers attach to the existing socket.

Profiles bootstrap

When SUPERSURF_EXPERIMENTS=profiles is set, main() (daemon/src/main.ts:402-429) does extra setup before the IPC server starts:

  1. Ensures ~/.supersurf/daemon/ exists for the PID log.
  2. Awaits ensureExtension() to download/refresh the extension bundle from GitHub.
  3. Constructs the ProfileRegistry rooted at ~/.supersurf/profiles/.
  4. Reads managed-pids.jsonl via replayPidLog(), computes orphans (findOrphanPids), and SIGTERMs them via killOrphanPids().
  5. Truncates the PID log.

This orphan-cleanup pass is the daemon's only crash-recovery mechanism for managed Chromium.

2. IPC layer (daemon/src/ipc.ts)

Socket and protocol

The Unix domain socket lives at ~/.supersurf/daemon.sock. IPCServer.start() calls net.createServer().listen(socketPath). Each MCP server connects, completes a handshake, then upgrades to NDJSON JSON-RPC 2.0.

Handshake protocol

1. MCP server  ─▶  daemon : { type: "session_register", sessionId: "..." }\n
2. daemon      ─▶  MCP    : { type: "session_ack",
                              browser: "chrome",
                              buildTimestamp: "...",
                              capabilities: { profiles: bool } }\n
   (or)        ─▶  MCP    : { type: "session_reject", reason: "..." }\n
3. ...steady-state JSON-RPC 2.0 over NDJSON...

Notable details from IPCServer.handleConnection():

  • The pre-handshake connection accepts a daemon_status query (used by supersurf-daemon status) without auth and closes immediately after the response.
  • Duplicate sessionIds are rejected with “Session ID already in use”.
  • After successful handshake the session is added to SessionRegistry and RequestScheduler, and setSessionCountCallback is invoked.

Capabilities negotiation

The session_ack includes capabilities: { profiles: !!this.profileRegistry }. The server's DaemonClient parses this and stores it as daemonCapabilities so the backend can decide whether to expose profile-related MCP tools.

Request routing

handleRequest() (daemon/src/ipc.ts:229) is the dispatcher. It validates JSON-RPC 2.0 shape, then routes by method:

Method namespaceRouted toSkips scheduler?
profiles.*handleProfileRequest()yes — direct
experiments.*handleExperimentRequest()yes — direct
anything elsescheduler.enqueue()no — round-robin queued

isProfileMethod() and isExperimentMethod() (daemon/src/profiles/types.ts:52, daemon/src/experiments/types.ts:20) are the membership tests. Methods themselves: profiles.create, profiles.list, profiles.delete, profiles.connect, experiments.toggle, experiments.get, experiments.getOne.

Session disconnect cleanup

When the IPC socket closes (daemon/src/ipc.ts:182-220):

  1. scheduler.removeSession() rejects queued requests for the session.
  2. sessions.remove() and experiments.deleteSession() clear state.
  3. The extension is notified via a sessionDisconnect JSON-RPC notification so it can ungroup the session's tabs.
  4. If the session was bound to a profile: the daemon checks whether any other sessions still reference that profile. If not, it SIGTERMs the Chromium PID and writes a kill log entry — managed Chromium dies as soon as the last consumer leaves.

Profile request handler

handleProfileRequest() (daemon/src/ipc.ts:316-411) gates all profile methods behind profileRegistry !== null. The most interesting branch is profiles.connect:

  1. Verify the profile exists.
  2. If Chromium isn't running, queue a bootstrap via matchmaker.enqueueBootstrap(). Inside the queued task: double-check (under serialization), add to pendingSpawns, call spawnChromium(), attach an exit listener that clears the running PID and writes a kill log entry.
  3. Call matchmaker.requestMatch(profile, 90000) and await the matching extension connection (90s ceiling).
  4. If this was the first launch (!isInitialized), call markInitialized().
  5. Bind the session to the profile via sessions.setProfileId().
  6. Apply per-profile experiment defaults from ProfileConfig.experiments.

3. Extension bridge (daemon/src/extension-bridge.ts)

HTTP + WebSocket server

ExtensionBridge.start() (daemon/src/extension-bridge.ts:86) creates an http.Server on 127.0.0.1:5555 (default) and attaches a WebSocketServer to it via ws. The HTTP layer exists for one reason: profile registration pages.

Registration HTTP endpoint

When profilesEnabled, GET /register/<name> (regex ^/register/([a-z0-9][a-z0-9-]*)$) responds with a tiny HTML page that uses window.postMessage to send { __supersurf: true, action: 'register-profile', profile: <name> }. The content script in the extension picks this up and announces the profile back over WebSocket. The response also sets a cookie:

Set-Cookie: supersurf_profile=<name>; Path=/; SameSite=Lax

This cookie is the failsafe for profile re-attachment: even if chrome.storage.local is wiped, the next WebSocket upgrade carries the cookie and the bridge can pull the profile name out of it (daemon/src/extension-bridge.ts:135-143).

Single-connection vs pooled mode

  • profilesEnabled = false (default): the bridge rejects any new connection while one already exists, sending a JSON-RPC error -32001 "Another browser is already connected. Only one browser at a time." and closing with WebSocket code 1008 after 100ms.
  • profilesEnabled = true: every connection is added to the Matchmaker pool and matched by profile name.

Connection setup

For each accepted WebSocket (daemon/src/extension-bridge.ts:114-174):

  1. Cookie is parsed for supersurf_profile=<name>.
  2. A PooledConnection is constructed: { ws, profile, browser, buildTimestamp, pingInterval, inflight }.
  3. A 10s ping keep-alive interval is started.
  4. The connection is added to the matchmaker pool (which immediately tries to satisfy any pending matches).

Message handling

handleMessage() recognizes four kinds of inbound messages:

  • JSON-RPC responses (id !== undefined && !method) — looked up in conn.inflight, resolved or rejected. If the result includes a currentTab field, onTabInfoUpdate is fired (piggyback tab tracking).
  • type: 'handshake' — extracts browser, buildTimestamp, and any profile field. Updates the matchmaker connection state.
  • profile_announce notifications — the extension announces its profile post-registration (no JSON-RPC id).
  • Tab-info notifications (notifications/tab_info_update) — fires onTabInfoUpdate callback.

Outbound commands

Two send methods:

  • sendCmd(method, params, timeout) — for unmanaged (single-connection) callers; goes to matchmaker.getConnectionForProfile(null).
  • sendCmdToProfile(profile, method, params, timeout) — picks the correct pooled connection; throws if no extension matches the profile.

Both delegate to Matchmaker.sendCmd() which handles correlation IDs and timeouts.

4. Scheduler (daemon/src/scheduler.ts)

RequestScheduler is the single drain loop that serializes every command going to the extension. It enforces fairness across sessions and prevents tab-ownership violations.

Method classification

Three Set<string> constants partition the JSON-RPC method namespace (daemon/src/scheduler.ts:23-33):

  • TAB_CLAIM_METHODS = { selectTab, createTab } — a session is claiming/attaching a tab.
  • TAB_RELEASE_METHODS = { closeTab } — a session is giving up a tab.
  • TAB_SCOPED_METHODS = { navigate, snapshot, evaluate, screenshot, consoleMessages, networkRequests, clearNetwork, performanceMetrics, waitForReady, capturePageState, forwardCDPCommand, window, dialog, listExtensions, secure_fill } — must be executed on the session's attached tab.

Round-robin pick

pickNextRequest() walks sessionOrder starting from currentSessionIdx, returning the first non-empty queue's head, and advances the index. This guarantees fairness — no session can monopolize the loop.

Auto context-switching

For tab-scoped methods, before executing, the scheduler checks whether the session's attachedTabId matches the extension's currently-active tab (tracked per profile in currentExtensionTabIds). If they differ, an internal selectTab is sent first, then the actual command. The injected _sessionId parameter lets the extension keep tab groups isolated per session.

Tab ownership enforcement

Before executing selectTab or closeTab against a tabId, the scheduler checks sessions.findTabOwner(tabId). If another session owns it, the request is rejected with "Tab N is owned by session ‘X’. Cannot attach/close."

Profile-aware routing

executeRequest() reads sessions.getProfileId(sessionId) and routes via bridge.sendCmdToProfile(profileId, ...) when set, else falls back to bridge.sendCmd(...). The current-tab tracking map currentExtensionTabIds: Map<string|null, number|null> is keyed by profile so each managed Chromium has its own context-switch state.

getTabs filtering

When getTabs returns, the scheduler filters out tabs owned by other sessions so an agent only sees tabs it can legally touch. Handles both { tabs: [...] } and bare-array result shapes.

Drain on shutdown

drainAll() rejects every queued request with “Daemon shutting down” and clears state — called from main.ts's shutdown().

5. Session management

SessionRegistry is a thin Map<string, DaemonSession> with helpers. The session shape (daemon/src/types.ts:10):

export interface DaemonSession {
  sessionId: string;
  socket: net.Socket;
  ownedTabs: Set<number>;
  attachedTabId: number | null;
  groupId: number | null;
  profileId: string | null;
}

Notable methods:

  • add(id, socket) returns false if the ID is taken (collision-safe).
  • setAttachedTabId / getAttachedTabId — current focus.
  • addOwnedTab / removeOwnedTab / findTabOwner — ownership index.
  • setProfileId / getProfileId / getSessionsForProfile — profile bindings.
  • getOtherOwnedTabIds(sessionId) — used by getTabs filter.

6. Profiles subsystem

Profiles are off by default. The whole subsystem only initializes when the profiles experiment is in SUPERSURF_EXPERIMENTS.

FileRole
types.tsProfileConfig, PooledConnection, PendingMatch, PidLogEntry. isProfileMethod() routing test.
registry.tsCRUD for ~/.supersurf/profiles/<name>/. Name validation, initialized state, in-memory running PIDs.

ProfileRegistry

Constructor takes a directory (typically ~/.supersurf/profiles/) and mkdir -ps it. Per-profile layout:

~/.supersurf/profiles/<name>/
├── supersurf.json      # ProfileConfig
└── chrome-data/        # Chromium --user-data-dir

Name validation:

const RESERVED_NAMES = new Set(['false', 'true', 'null', '']);
const NAME_REGEX = /^[a-z0-9][a-z0-9-]{0,31}$/;

Names must be lowercase alphanumeric + hyphens, max 32 chars, no leading hyphen, and not in the reserved set. This matters because the name is interpolated into URLs (/register/<name>) and cookie values.

Lifecycle methods:

  • create(name, experiments?) — validates, creates dirs, writes config.
  • list() — directory scan, includes computed running flag.
  • get(name) — reads supersurf.json.
  • delete(name, sessions) — refuses if any session is bound to the profile; otherwise SIGTERMs the running PID and rm -rfs the directory.
  • markInitialized(name) / isInitialized(name) — first-launch gate.
  • setRunningPid / clearRunningPid / getRunningPid / isRunning — in-memory PID tracking. isRunning does a live process.kill(pid, 0) check and self-cleans dead entries.

Matchmaker

The matchmaker is the heart of profile-aware connection management.

class Matchmaker {
  private pool: Map<WebSocket, PooledConnection>;
  private pendingMatches: PendingMatch[];
  pendingSpawns: Set<string>;
  private bootstrapQueue: Promise<void> = Promise.resolve();
}

Connection pool

addConnection / removeConnection / updateProfile mutate the pool and call tryResolvePendingMatches() to satisfy any waiting agents. removeConnection drains all in-flight requests with “Extension disconnected” and clears the keep-alive ping.

Match resolution

requestMatch(profile, timeoutMs) (default 60s):

  1. Try findMatch(profile) for an immediate hit.
  2. Otherwise queue a PendingMatch. When a new connection arrives or a profile is updated, the queue is rechecked.

findMatch(profile) has two modes:

  • profile === null (unmanaged): blocked while pendingSpawns.size > 0 — this is the poaching prevention. Without it, an unmanaged caller could grab the WebSocket of a Chromium that was spawned for a profile but hadn't announced its profile yet.
  • profile === 'foo': direct lookup of any open connection with conn.profile === 'foo'.

Bootstrap queue

enqueueBootstrap(fn) chains operations onto a serial promise queue. The IPC layer uses this to ensure that two concurrent profiles.connect calls for the same uninitialized profile don't both spawn Chromium. Inside the queued function, the caller does a double-check (if (registry.isRunning(profile)) return;) before spawning.

Sending commands

sendCmd(conn, method, params, timeout) builds a JSON-RPC 2.0 request with an 8-char UUID id, stores resolve/reject in conn.inflight, sends, and starts a 30s default timeout.

chrome.ts — process management

Binary discovery

Checks these paths in order, then falls back to which:

/opt/homebrew/bin/chromium
/usr/local/bin/chromium
/usr/bin/chromium
/usr/bin/chromium-browser

If none exist, findChromiumBinary() returns null and spawnChromium() throws with “Chromium not found — install via brew install chromium”.

spawnChromium(profileName, extensionDir, port, isFirstLaunch)

<binary> \
  --user-data-dir=~/.supersurf/profiles/<name>/chrome-data \
  --load-extension=<extensionDir> \
  --no-first-run \
  --no-default-browser-check \
  --use-mock-keychain \
  [http://127.0.0.1:<port>/register/<name>]   # only on first launch

Spawned with detached: true, stdio: 'ignore', then child.unref() so the daemon doesn't block on it.

PID log (crash recovery)

managed-pids.jsonl is the daemon's append-only log of spawn/kill events. Helpers:

  • appendPidLog(entry) — append one { action, profile, pid, ts } line.
  • replayPidLog() — read all entries.
  • findOrphanPids(entries) — replay events, return PIDs that were spawned but never killed.
  • killOrphanPids(pids) — SIGTERM each and log a kill entry.
  • truncatePidLog() — wipe after recovery.

The daemon runs the orphan-cleanup pass exactly once at startup (when profiles are enabled), then truncates the log.

extension-source.ts

Downloads the SuperSurf extension from GitHub releases (LiquidBuiltIt/Supersurf) and caches to ~/.supersurf/extension/. ensureExtension():

  • Not cached: pullExtension() (mandatory — first-run blocking).
  • Cached: query GitHub for the latest tag and re-pull only if the version differs. Network failures fall through silently — the cached version is used.

pullExtension() downloads https://github.com/.../archive/refs/tags/<tag>.tar.gz to a mkdtempSync temp dir, extracts only */extension/ via tar xzf --strip-components=1, then flattens the nested extension/ directory. getExtensionDir() returns the cache path for spawnChromium() to pass via --load-extension.

7. Experiments subsystem

DaemonExperimentRegistry (experiments/index.ts) is the source of truth for which experiments each session has enabled. The MCP server caches this locally but reads/writes go through IPC.

Available experiments

const AVAILABLE_EXPERIMENTS = [
  'page_diffing',
  'smart_waiting',
  'storage_inspection',
  'mouse_humanization',
] as const;

Note that profiles is not in this list — it is a daemon-startup-only flag via SUPERSURF_EXPERIMENTS, not a per-session toggle.

Per-session state

Each session has its own Set<string> of enabled experiment names, lazily initialized from _defaults on first toggle() call. _defaults is populated once at startup via applyDefaults(envExpNames).

IPC methods

MethodBehavior
experiments.toggleSets enabled/disabled for (sessionId, experiment), throws on unknown experiment name.
experiments.getReturns Record<string, boolean> of every available experiment for the session.
experiments.getOneReturns { experiment, enabled } for a single experiment.

Env var defaults

SUPERSURF_EXPERIMENTS=page_diffing,smart_waiting,profiles enables those at startup. main.ts parses the comma-separated list, calls experiments.applyDefaults(...) (which silently ignores profiles because it's not in the available list), and uses envExpNames.includes('profiles') to decide whether to bring up the profile subsystem.

Profile-bound defaults

When a session calls profiles.connect, the IPC handler reads ProfileConfig.experiments and toggles them on for that session. This is how a profile can carry “always enable mouse_humanization” semantics across sessions.

8. Test coverage

Vitest unit tests cover every daemon module. main.test.ts exercises PID file lifecycle, parseArgs, formatUptime, and stopDaemon cleanup. ipc.test.ts connects real sockets against a mocked bridge and verifies the handshake, NDJSON routing, session disconnect, concurrent sessions, profile/experiment IPC routing, and the capabilities header. scheduler.test.ts covers round-robin fairness, tab ownership rejection, auto context-switch, and the getTabs filter. session.test.ts covers SessionRegistry CRUD, ownership tracking, and profile bindings. experiments.test.ts covers per-session isolation, default inheritance, env var defaults, and IPC behavior. The profiles/ test directory has unit tests for types, registry, chrome, extension-source, and matchmaker.

9. Known troubleshooting — profiles.connect timeout

If a managed profile's chrome.storage.local loses its supersurf_profile key (force-killed Chromium, manually removed extension, Chrome corruption), the extension reconnects as unmanaged. The matchmaker can't satisfy requestMatch(profile) and the IPC handler eventually times out after 90s. The fix is to relaunch Chromium with the registration URL so the cookie + content-script path re-sets the storage key:

pkill -f "chromium.*PROFILE_NAME/chrome-data"
/opt/homebrew/bin/chromium \
  --user-data-dir=~/.supersurf/profiles/PROFILE_NAME/chrome-data \
  --load-extension=~/.supersurf/extension \
  --no-first-run --no-default-browser-check --use-mock-keychain \
  "http://127.0.0.1:5555/register/PROFILE_NAME"

A long-term fix (always opening the registration URL on every spawn, or falling back to chrome.cookies reads) is pending.
